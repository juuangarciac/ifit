================================================================================
AUDITORÍA DE ENDPOINTS / ACTIONS - IFit/Services/
Fecha: 2026-06-15
Objetivo: identificar qué endpoints usa estrictamente el cliente MAUI y cuáles NO.
Método: cada método de servicio cruzado con sus llamadas reales desde
        ViewModels, Views y App.xaml.cs.
================================================================================

RESUMEN EJECUTIVO
--------------------------------------------------------------------------------
- Endpoints REALMENTE usados por el cliente: ~24
- Métodos / endpoints definidos pero NUNCA invocados: ~30
  (sobre todo CRUD de administración y métodos duplicados)

Nota: WebService, DatabaseService, NotificationService e ISecureStorageService
no exponen endpoints propios (transporte HTTP genérico / SQLite local / UI),
por lo que el análisis se centra en los servicios de dominio.

================================================================================
OBSERVACIONES
================================================================================
1. PATRÓN: el cliente solo consume lectura de catálogos + flujo de
   onboarding/rutinas/chat. Todo el CRUD de administración (crear/editar/borrar
   usuarios, cuestionarios, coaches, niveles) está implementado pero es código
   muerto en la app móvil (pensado para un panel admin ajeno al cliente).

2. DUPLICADO: TrainingService.generateRoutineAsync y
   AIRoutineService.GenerateRoutineAsync pegan al mismo POST /routines/generate.
   Solo el de AIRoutineService se usa (soporta coachType y note).

3. BUG: el logout nunca llama a /auth/logout ni limpia los tokens seguros
   (SecureStorage). ProfileViewModel.LogoutAsync solo hace Preferences.Clear().

4. DOC vs CÓDIGO: el docstring de AIRoutineService dice POST /chat/{coachName},
   pero el código real construye POST /{coachName}/chat (p.ej. /ronnie/chat).
